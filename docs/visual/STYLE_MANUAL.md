## 1. 已确认方向与不可静默改变的产品联系

### 1.1 已确认

- **整体方向**：`“锈蚀末日霓光”`，状态 `user_confirmed`（Creative Brief v0.3 §7.1 确认的高层视觉方向；仅整体方向被接受）。
- **题材**：V1｜末日生存，`user_confirmed`。
- **核心体验联系**：PC 优先；移动躲避 + 自动攻击；以清屏规模感为主爽感来源，以击杀反馈重量为辅助爽感来源；目标是解压而非刁难。
- **第一 Vertical Slice 意图**：验证易懂移动、自动攻击循环、可感知清屏爽感，以及至少一次 B2 关键词组合带来的明显变强。
- **构筑方向**：B2｜关键词组合，`user_confirmed`；具体关键词与组合表现未定。
- **局外方向**：O2｜局外构筑收藏，`user_confirmed`；具体收藏承载未定。

> Creative Brief v0.3 §7.1 的确认仅覆盖高层视觉基线。具体调色、材质、镜头、特效密度、UI 规则，以及 B2/O2 的视觉承载仍为 `team_proposal` 或 `unresolved`。

### 1.2 不应被改变的联系

以下是产品联系，不是可被美术偏好覆盖的装饰选项：

1. 视觉必须让敌潮规模、清除成果和力量跃迁可被感知，不能只追求末日氛围而牺牲清屏读数。
2. “锈蚀”提供衰败、磨损和重量；“霓光”提供状态、危险、奖励和力量跃迁的可见信号。两者应形成可读对照，不能互相混成脏灰或纯霓虹炫技。
3. 末日生存可以有压迫环境，但玩家体验不能被视觉表达成持续惩罚、恐怖压制或难以辨识的混乱；“解压”不等于没有压力，允许敌潮造成可读压力，但视觉不能让压力长期压过玩家掌控感，应让玩家看到压力被转化为空间和清除成果（`team_proposal`）。
4. 自动攻击与移动躲避的直接性必须保留；视觉不应要求玩家依赖复杂瞄准或阅读长篇说明。
5. B2 与 O2 的承载应帮助玩家识别“我正在形成一种组合/收藏”，不应用繁复装饰替代可理解的力量变化。

除以上用户确认联系外，具体造型、角色、敌人、场景、色值、字体、特效方案均为 `team_proposal` 或 `unresolved`。

## 2. 视觉目标与非目标

### 2.1 视觉目标（具体规则为 `team_proposal`）

- 在中等信息密度与敌潮规模中，优先保持玩家、危险、敌潮、奖励四类信息的瞬时区分。
- 让“生锈的旧世界”与“正在过载的新能量”同时存在：底层沉重、表层信号鲜明。
- 用轮廓、局部高亮、材质反差和节制的发光承载击杀重量，不依赖全屏闪烁。
- 让力量跃迁产生阶段性视觉升级，但仍让玩家一眼认出自己、敌潮和场地边界。
- 让 UI、收藏和战斗反馈共享同一套材质与色彩语法，而不是另起一套风格。
- 允许 2D、VFX、UX/UI、技术美术在没有图片 anchor 的情况下先按同一规则提出候选；最终一致性须等待审阅与 anchor 门。

### 2.2 非目标

- 不追求写实军事末日、纯恐怖、纯赛博朋克霓虹秀或无差别高饱和卡通化。
- 不用噪点、锈斑、烟尘、镜头效果和发光遮盖关键可读信息。
- 不把敌人数量、屏幕覆盖率或闪烁强度本身当成爽感全部来源。
- 不为本手册锁定最终角色设定、武器清单、敌人清单、地图、数值、字体文件、资产尺寸或渲染技术。
- 不把 B2 偷换成连击引爆/打击链产品；任何具体组合机制仍需后续设计授权。
- 不把 O2 偷换成高惩罚刷宝或永久数值碾压；局外收藏的具体强度仍未决。

## 3. “锈蚀末日霓光”的视觉语法

> 下列配方是 `team_proposal`，不是逐项批准的最终审美规则。

**底层衰败 → 中层实体 → 上层信号 → 瞬时高潮**：

1. **底层衰败**：低明度、低至中饱和的铁锈、煤灰、旧混凝土、氧化铜、污水色族，构成环境和非关键表面。
2. **中层实体**：偏暖的锈红、土黄、旧钢、骨白等较稳定色族，区分玩家/敌人身体与可碰撞实体的体量。
3. **上层信号**：有限的冷青、电蓝、酸黄、紫红霓光，用于状态、危险、奖励、组合和力量跃迁。
4. **瞬时高潮**：清屏和重击可短暂扩大亮度/面积/色彩对比，但结束后必须回落，避免持续高潮抹平层级。

**约束**：任何单一资产不应同时把所有层级都做成高亮；霓光应像电力、警示或异变在锈蚀世界上的“有意义泄漏”，而非均匀描边。

## 4. 调色板关系与语义

不在 v0.2 锁定最终色值；示例仅为方向和色族，后续须由 Director/用户审阅。`team_proposal`。

| 色族 | 示例方向（非最终色值） | 主要语义 | 使用关系 |
|---|---|---|---|
| 炭黑/煤灰 | 深灰、蓝黑、脏黑 | 背景深度、留白、危险前的沉静 | 大面积底色；避免纯黑吞掉轮廓 |
| 铁锈/氧化红 | 锈红、砖红、暗橙 | 末日环境、磨损、实体重量 | 环境和旧物为主，不独占敌人语义 |
| 尘土/骨白 | 灰黄、旧白、沙色 | 结构边缘、文本底、干燥材质 | 作为中性分离色，不作全屏高亮 |
| 冷青/电蓝 | 青绿、蓝青、电蓝 | 玩家状态、可用能量或正向反馈候选 | 必须与环境暖锈形成对照；具体归属未决 |
| 酸黄/警示黄 | 黄绿、酸黄、警示橙 | 危险、精英、临界状态候选 | 不可同时编码所有稀有度 |
| 紫红/洋红 | 暗紫、紫红、过载红紫 | 高威胁、稀有、组合完成候选 | 需控制面积，避免和受伤/错误混淆 |
| 低饱和绿 | 灰绿、氧化铜绿 | 收藏、修复、局外承载候选 | 具体是否为 O2 语义 `unresolved` |

### 4.1 颜色使用规则

- 颜色只做一层编码；重要信息必须同时有形状、轮廓、位置、纹理、图标或文字支持。
- 环境优先低明度/低饱和；玩家与关键反馈通过明度、边缘清晰度或局部冷色获得分离。
- 敌潮可共享有限色族以形成规模，但普通敌人、精英和奖励必须再靠轮廓/标记区分。
- 发光色要有“来源”和“用途”：同一色族不应无理由同时代表玩家、危险和收藏。
- 色盲与低亮度场景下不能依赖红绿、蓝紫或明暗单一差异；具体可访问性验收留待 UX/UI 与 QA。

## 5. 材质语言

### 5.1 环境（`team_proposal`）

- 以旧钢、剥落涂层、氧化边缘、粗糙混凝土、尘土与潮湿污渍建立耐久感和年代感。
- 材质变化集中在边缘、连接处、受力处和积尘处；避免全表面均匀贴脏。
- 环境细节应服从略俯视下的路径和战场留白；高频纹理不应覆盖玩家移动区域的主要识别面。

### 5.2 玩家（`team_proposal`）

- 轮廓先于材质细节；服装/装备可有磨损，但主形体必须比环境更稳定、更易识别。
- 玩家材质应包含一种可持续识别的“功能性信号”候选（冷色电源、反光边、布料色块或局部霓光），具体方案 `unresolved`。
- 受击、强化、组合完成等状态改变优先通过局部结构/信号变化表达，不将玩家整体长期变成发光团。

### 5.3 普通敌人（`team_proposal`）

- 形体可重复、材质可共享，以群体节奏和轮廓差异形成规模；不为每个个体堆叠独立细节。
- 普通敌人使用较少的高亮面；其“可被清除”状态应清楚，不应与环境锈斑融为一体。
- 群体颜色/材质可有轻微变体，但不得导致玩家需要逐个阅读。

### 5.4 精英/高威胁目标（`team_proposal`）

- 通过体量、轮廓突变、稳定的局部信号、材质完整度或不寻常的光源方向表达威胁，而不是只提高饱和度。
- 精英应在敌潮中先被识别为“结构不同”，再被识别为“颜色不同”；具体标识形态 `unresolved`。
- 高威胁目标的视觉重量不得压过玩家可控感；需保留明确弱点/状态/反馈的表达空间，规则待 Director 审阅。

### 5.5 收藏/界面（`team_proposal`）

- 收藏与 UI 可使用较干净的金属、树脂、玻璃、标签纸或电路板语汇，体现“从废墟中整理出可复用资源”。
- UI 面板可比战场更整洁，但仍保留锈蚀结构、磨损边缘或霓光状态条中的至少一种共同 DNA。
- 收藏对象应有可识别的家族形状与状态层级；具体收藏形态、稀有度和 O2 规则 `unresolved`。

## 6. 轮廓、层级与可读性

### 6.1 层级优先级（`team_proposal`）

在任何战斗画面，优先级为：

1. **玩家**：最稳定、最连续的识别轮廓；移动方向与当前状态不能被遮挡。
2. **即时危险**：接触风险、危险区域、精英攻击预兆等；用强边缘/节奏/形状变化，而非仅靠颜色。
3. **敌潮**：整体规模、流向和密度可读；个体细节让位给群体结构。
4. **奖励/拾取/组合信号**：在安全不遮挡的位置有清晰局部亮点，不能伪装成危险。
5. **环境**：提供空间、方向和末日氛围，但不抢夺前四层的视觉预算。

### 6.2 轮廓规则

- 玩家轮廓使用稳定的外形节奏与清晰的负形；敌人轮廓允许重复但须有类别级差异。
- 危险优先使用可预期的形状语言（尖锐、扩张、断续边缘等候选），奖励使用聚拢、上扬、环绕或标签化语言候选；具体语法 `unresolved`。
- 敌潮的“多”由间距、方向、密度、遮挡关系和共同节奏表达，不由无限增加细节表达。
- 不用全体对象统一描边作为唯一解决方案；描边、投影、明暗分离和局部光边应按层级组合。

## 7. 光照、对比、留白、构图与镜头

### 7.1 光照与对比（`team_proposal`）

- 环境光建立低明度的锈蚀底；关键实体用局部方向光或霓光边缘建立分离。
- 高对比留给玩家、即时危险、关键击杀和奖励确认；环境与普通敌群避免处处硬对比。
- 霓光应有核心、过渡、衰减三层观感；不把整片对象变成均匀平面发光。
- 击杀高潮允许短暂提高对比，但必须保留玩家与危险的可识别边界；屏幕整体白闪、重度色偏等候选效果需独立审阅。

### 7.2 留白与构图（`team_proposal`）

- 玩家周围保留可读的呼吸区；敌潮可围压画面，但不能让玩家轮廓长期处于不可恢复的满屏遮挡。
- 画面构图优先呈现“玩家—敌潮流向—可移动空间”的关系，而不是中心堆叠所有特效。
- 清屏高潮应有视觉前后关系：蓄势/压迫 → 清除路径或扩散 → 余波/奖励确认；不要从第一帧到最后一帧都满载。
- 局外收藏与 UI 构图使用卡片/标签/槽位等可扫描结构候选，避免把信息埋入纯装饰纹理。

### 7.3 创意仲裁规则（`team_proposal`）

当环境氛围、霓光表现、击杀重量与战场可读性冲突时，优先保留玩家轮廓、即时危险、移动空间和清屏结果；其次保留击杀重量；最后才保留环境细节与装饰性霓光。此规则是创意优先级，不是技术实现规格。

### 7.4 略俯视镜头原则（`team_proposal`）

- 略俯视用于同时读取地面空间、敌潮方向、玩家周边留白和掉落/奖励位置。
- 地面透视与纹理方向要辅助移动路线，不制造错误的深度或倾斜感。
- 前后层级通过遮挡、明度、接触阴影和尺度变化表达；不得依赖镜头摇晃来证明重量。
- 镜头具体角度、缩放、屏幕占比、相机运动均 `unresolved`，不在本手册锁定。

## 8. 清屏规模感与击杀反馈重量

主爽感为清屏规模感、辅助爽感为击杀反馈重量（两者 `user_confirmed`）；以下分级表达是 `team_proposal`。

### 8.1 普通击杀：可连续读取的“单位重量”

- 反馈短、清楚、可重复：命中位置有局部形变/亮度变化/碎屑或消散方向候选。
- 单个击杀不应制造足以遮挡下一个危险的全屏事件；重点是让连续清除形成稳定节拍。
- 普通敌人反馈应共享家族语言，以便玩家快速把大量反馈整合为“我正在清掉一片”。

### 8.2 精英/高威胁击杀：可识别的“重量升级”

- 比普通击杀拥有更长的视觉确认窗口、更明确的形态破坏或更集中光源，但仍不夺走玩家位置与下一危险的可读性。
- 反馈结构应说明“这不是普通单位”，可由体量塌缩、装甲断裂、核心熄灭、余波或奖励标志候选组合表达；具体表现 `unresolved`。
- 精英击杀的色彩/声音联动（若未来需要）不能在本手册中假称已实现；这里只规定视觉语义。

### 8.3 清屏高潮：可感知的“规模结果”

- 视觉重点不是同时放大每个击杀，而是显示敌潮结构被成片改变：密度下降、路径打开、残骸/光线向外扩散、奖励/组合结果汇聚等候选。
- 高潮需有前置积累与后置余波，让玩家看到“刚才的压力被我转化成空间和成果”。
- 高潮使用更大的空间关系和更宽的亮度层级；仍需保持玩家轮廓、危险预兆和可移动空间。
- 规模感应来自多单位关系、清除路径、节奏同步和空间重获，不以粒子数量、屏幕闪光或数值跳字作为唯一依据。

## 9. B2 关键词组合与 O2 局外构筑收藏

### 9.1 B2｜关键词组合的视觉语法（方向已确认，具体语法 `team_proposal`）

- **单关键词**：使用一个稳定的形状/色族/材质标志，能在战斗中快速回认。
- **组合形成**：两个或多个关键词共同出现时，改变反馈的结构关系（例如轮廓叠层、光路连接、材质相容或清屏轨迹改变），而不是简单叠加更多装饰。上述只是“可见变强”的视觉表达示例；不决定 B2 的关键词、组合规则、系统机制、数值或实现。
- **力量跃迁**：组合完成应有一次可识别的“现在更强”状态确认；持续状态与瞬时确认要区分。
- **避免语法**：不要把所有组合都表达为彩虹色、爆炸、巨大图标或复杂文字；组合必须服务清屏可读性。
- **家族一致性**：同一关键词在玩家、反馈、UI、收藏中共享核心标志，但允许按媒介改变细节密度。
- 关键词名称、数量、组合规则、稀有度、顺序、是否影响局外收藏均 `unresolved`。

### 9.2 O2｜局外构筑收藏的视觉承载（方向已确认，具体承载 `team_proposal/unresolved`）

- 收藏对象应看起来像“可带入下一次尝试的构筑线索”，而不只是货币或装饰徽章。
- 每个收藏家族需要稳定的轮廓母题、材质母题和状态标记，以便玩家在列表中快速分组。
- 未解锁、已获得、可组合、已装备/已纳入选择空间等状态必须同时有图形、布局、纹理或文字区别，不能只换颜色。
- UI 的整理感可以高于战场，但保留锈蚀来源与霓光状态的共同语法，避免局外系统像另一款产品。
- 收藏不应视觉上承诺尚未确定的永久强度、稀有度或公平性；这些内容留待系统与用户决策。

## 10. UI、文字、图标与非颜色编码

以下是 `team_proposal`，需由 UX/UI 与 Game Director 复核：

- **文字层级**：标题/状态/操作/辅助说明使用明确字号、重量、间距和容器层级；不依赖发光或纹理来制造层级。
- **文字底**：在锈蚀纹理、霓光和战斗背景上提供足够的稳定底面/遮罩/留白；文字不能直接压在最高频材质上。
- **图标**：优先轮廓、内部负形和少量语义纹理；缩小时仍应认出类别，不以复杂渐变证明品质。
- **状态**：可用、锁定、选中、危险、完成、收藏等状态至少同时使用两种编码：形状/位置/图案/边框/文字/动势/明度中的任意两种；颜色只是辅助。
- **颜色非唯一编码**：红/绿、蓝/紫、亮/暗不得单独承担敌我、稀有度、错误/成功或解锁/锁定的区别。
- **动画保留**：若未来添加闪烁、脉冲或飘字，必须保留静态可读状态；不可把信息只放进转瞬即逝的动态效果。
- **可访问性门**：对比度、色盲、缩放、长文本、低亮度和屏幕拥挤的正式验收尚未发生，状态 `unresolved`，由 UX/UI 与独立 QA 后续负责。

## 11. First Vertical Slice 视觉范围上限与 non-goals

### 11.1 三层视觉范围边界

以下是服务最小核心爽感验证的视觉验证边界提案，不是开发任务，也不把整套长期视觉系统变成当前必须交付；具体制作仍需后续 Producer/Charter/用户阶段门。

**核心必需（必须服务本次最小核心爽感验证）**

- 玩家可识别轮廓。
- 普通敌潮。
- 自动攻击反馈。
- 清屏规模与清除后空间结果。
- 普通击杀的最小重量表达。
- 至少一次 B2 组合带来的可见变强（仅验证视觉结果，不规定关键词、组合规则、系统机制、数值或实现）。

**可选候选（不构成当前必做门槛）**

- 精英/高威胁目标表达。
- 更重的独立击杀层级。

若未纳入本次 Slice，不得将其视为缺项。

**后置（不纳入当前 Slice 必做）**

- O2 局外构筑收藏承载。
- 完整局外 UI。
- 完整 UI 体系/收藏状态系统。
- 完整反馈库和多套资产。

战斗空间仍可提出支持“锈蚀末日霓光”关系的候选，但不应以扩大长期系统为由进入当前必做门槛。

### 11.2 Non-goals

- 不追求完整敌人生态、Boss、完整地图内容、长线内容或完整局外系统。
- 不追求完整美术资产库、最终风格锁定、全套角色/武器/收藏图鉴或多平台适配。
- 不用额外内容量掩盖清屏规模感和击杀重量尚未被证明的问题。
- 不在本手册中定义 Godot 节点、Shader、粒子数量、动画帧数、数值、代码结构、导出或性能实现。

## 12. 风险、反漂移检查表与下游交接

### 12.1 主要风险（`team_proposal/unresolved`）

- 锈蚀细节过密，环境噪声吞掉玩家、危险和清屏路径。
- 霓光过量，所有对象都成为同等重要的发光轮廓，层级坍塌。
- 末日压迫感压过解压承诺，画面让玩家感到被惩罚而非掌控。
- 普通、精英、奖励共享同一高亮色，导致战斗决策误读。
- 击杀反馈只剩闪光与数字，缺少“敌潮结构被清除”的规模关系。
- B2 组合变成装饰标签堆叠，玩家看不出组合带来的力量变化。
- O2 收藏变成独立的稀有度/货币界面，和局内构筑失去视觉联系。
- 没有 approved anchor 时下游各自解释“锈蚀末日霓光”，导致风格漂移。

### 12.2 反漂移检查表

每个下游候选（Concept Art、2D、VFX、UX/UI、技术美术）交接时应回答：

- [ ] 是否明确标注了 `user_confirmed`、`team_proposal`、`unresolved`？
- [ ] 是否能一眼区分玩家、危险、敌潮、奖励和环境？
- [ ] 锈蚀是否主要提供底层材质与重量，而非覆盖全部信息？
- [ ] 霓光是否有明确语义、来源和面积上限，而非平均发光？
- [ ] 是否保留了玩家周围留白与移动路径？
- [ ] 普通/精英/清屏高潮是否具备递进而不互相覆盖的层级？
- [ ] 清屏规模感是否通过敌潮关系和空间结果表达，而非只靠特效数量？
- [ ] 击杀是否有局部重量，同时不遮挡下一危险？

### 12.3 下游交接

- **Concept Art**：先依据本手册提出候选设定；任何 anchor 必须单独制作并交 Game Director 审阅，不能由本角色自批。
- **2D**：制作前引用材质、轮廓、色族和层级规则；不得自行发明新的主色语义。
- **VFX**：引用普通/精英/清屏三级反馈和霓光面积原则；不得让特效吞掉玩家或危险层级。
- **UX/UI**：引用锈蚀底、霓光状态和非颜色编码原则；具体可访问性须独立验证。
- **技术美术**：把规则转译为可实现的材质/光照/导入约束时，不能把本手册改写成已批准的技术方案；技术冲突回 Tech Lead，创意冲突回 Game Director/用户。
