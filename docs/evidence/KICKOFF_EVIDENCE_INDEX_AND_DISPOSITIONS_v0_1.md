### 4.3 Status and verdict semantics

Required operational statuses include:

- `planned` — future record is defined but not executed; cannot imply a result.
- `awaiting_artifact` — the row awaits a required artifact; no artifact is claimed.
- `observed_static_only` — only static/source or synthetic/anchor material was observed; never a runtime pass.
- `missing` — required artifact, identity, link, or source is unavailable/unverifiable.
- `schema_incompatible` — exact comparison cannot be made under declared schema/config/identity; never pass.
- `retest` — a new observation is linked to an original record; original remains preserved.
- `superseded` — a later explicit record is linked; original remains retained and inspectable.
- `blocked` — an authority-valid blocker prevents closure; not a pass.

The index may also use `not_run`, `not_ready`, `no-runtime-evidence`, and `inconclusive` where applicable. No status means approval. A `pass` verdict can only be issued by Independent QA/Release under a future authorized review and never from static prose. `verdict` is separate from `status`; missing or incompatible evidence cannot be converted into pass by relabeling.

### 4.4 Evidence class firewall

- `static/source`: proves source text, provenance, ownership, and proposal structure only.
- `synthetic/anchor`: proves a referenced static visual baseline only; not runtime readability or final art acceptance.
- `runtime`: future observed game behavior/state/input evidence.
- `QA`: future independent comparison/verdict evidence.
- `visual QA`: future independent frame/readability/aspect evidence.
- `performance`: future measured timing/frame evidence with named hardware/settings/clock.
- `export/release`: future artifact launch/integrity/release-review evidence.

These classes are non-interchangeable. Static/source or synthetic/anchor records cannot be runtime placeholders, and an empty planned row cannot be represented as an observed artifact.

## 5. Proposed retention and location contract (not frozen)

### 5.1 Canonical intended location and naming

- Intended repository-relative location: `docs/evidence/index/`.
- This task **does not create** that directory or any file inside it. The sole created artifact is this file in `docs/evidence/`.
- Proposed human-readable manifest pattern: `EVIDENCE_INDEX_<gate-or-scope>_<version>.md`.
- A machine-readable companion is optional and requires explicit Producer/Tech/QA authority review; it is not created or assumed here.
- Each manifest entry must declare `index_format_version`, status (`empty`, `partial`, or `populated`), owner, source set, coverage, and last review point.

### 5.2 Entry, reference, and access rules

Each entry must point to the actual artifact through `artifact_location` and stable `index_ref`, not merely repeat a prose claim. Repository-relative paths are preferred. External artifacts require a stable locator/digest, an `access_owner`, retrieval instructions or access boundary, and an explicit unavailable state when retrieval fails.

Raw logs, traces, snapshots, frames, reports, exported artifacts, and source references must retain their identity and be linked from the manifest. `evidence_id` is immutable and unique. No silent overwrite, in-place mutation of a failure, or reuse of an ID is allowed. Corrections create an appended record or explicit disposition with a new identity.

### 5.3 Retention classes and review behavior

The following classes are proposed, pending Producer/QA authority review and any User decision required by release or cost crossing:

| Proposed class | Intended behavior |
|---|---|
| `source-governance` | Retain with the governing decision/review chain while the Charter and readiness record remain active; review at governance transition |
| `synthetic-reference` | Retain the Anchor/reference and its decision provenance; v0.2 does not replace v0.1 silently |
| `raw-observation` | Retain raw frames/logs/traces/snapshots with the derived record and identity; review only by explicit disposition |
| `qa-verdict` | Retain verdict, observer, deviations, block, and retest lineage for the full affected gate/release review chain |
| `failure-blocker` | Preserve original failures and blockers through retest and closure; never delete because a later retest passes |
| `superseded-lineage` | Mark superseded and retain original plus successor links; no retroactive rewrite |
| `external-reference` | Retain locator, digest, access owner, and retrieval status; unavailable external material is `missing`, not assumed |

Durations, storage technology, backup policy, archive schedule, and deletion/expiry dates are **pending / unresolved**. Any expiry or deletion must be an explicit Producer disposition with QA visibility and a named authority record. Retention cannot erase disagreement, unresolved deviations, failed evidence, or the original observer record.

### 5.4 Missing, blocked, and superseded handling

`missing` means a required artifact or identity is unavailable or unverifiable. `blocked` means an applicable authority has stopped closure. `schema_incompatible` means exact comparison is invalid. These states remain visible in the index and cannot be collapsed into `not_applicable` or pass. A retest creates a new ID, carries `retest_of`, records the new source/build/config/fixture identity, and may use `supersedes` only as a lineage statement. The original failure remains intact.
